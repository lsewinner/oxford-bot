- Personal connections use authenticated functions and encrypted credentials; Microsoft uses user-bound PKCE, opener-authenticated exchange and CAS refresh rotation. Outlook/Teams/Outlook Calendar share the callback but isolate provider state, scopes and Graph allowlists; calendar event creation is a confirmed write and Teams targets organizational accounts. Direct requests use fixed hosts without redirects (why: prevent credential leaks and cross-account/service access).
- Provider connections allow multiple accounts per service, unique on (user, connector, account_key); Microsoft keys use Graph IDs with separate display labels; model tools take an optional `account` and proposals persist the resolved account (why: confirmed writes must hit the chosen account even when its email changes).
- Yuque uses personal tokens on a fixed host and persisted confirmation for document creation/replacement; bounded list pages expose continuation (why: prevent credential leaks, silent writes and incomplete-list claims).
- Google Calendar shares the Google OAuth client/callback with Gmail/Drive as a separate per-product connection; event creation is a confirmed write (why: one-click consumer auth, no silent calendar changes).
- Notion one-click OAuth uses its own callback and HMAC state, storing the workspace token as a personal_token row so execution shares the integration-token path; manual tokens remain a developer fallback (why: one-click consumer auth without duplicating Notion API code).
- GitHub one-click OAuth (github-oauth.server.ts) exchanges the code itself and keys the saved row by `gh-<user id>` as personal_token, so execution reuses the personal-token path and multiple accounts stay distinguishable; the manual token form remains a developer fallback (why: consumer users must not create apps or paste secrets).
- Slack one-click OAuth (slack-oauth.server.ts) mirrors GitHub: the code exchange stores the bot token as a personal_token row keyed `slack-<team id>` with the workspace name as label, and the old app-user-connector button is gone (why: consumer users authorize in one click; multi-workspace stays distinguishable).
- WeChat Customer Service (wechat_kf_accounts, server-only table) stores per-enterprise encrypted Secret/Token/AESKey; the public callback /api/public/wechat-kf/$accountId verifies the WeCom signature and CorpId before syncing, and claims the sync cursor by compare-and-set before replying (why: unauthenticated callback, retries must not double-reply).
- Airtable OAuth uses encrypted user-bound PKCE state and opener-authenticated exchange; a tagged JSON credential shares existing personal_token rows, with cached access tokens and owner-scoped CAS refresh leases; plain PATs remain unchanged (why: preserve accounts and prevent concurrent use of rotating refresh tokens).
- ClickUp one-click OAuth (clickup-oauth.server.ts) uses encrypted user-bound state without PKCE or scopes, exchanges the code with developer credentials in the JSON body, and saves the non-expiring access token as a personal_token row keyed `cu-<user id>`, so execution and the manual token form share one path (why: consumer users authorize in one click without creating apps, and existing ClickUp calls keep working).
